# ZITRO Admin Dashboard — Manual / Real-Time Test Scenarios

> **Purpose:** a human-executable QA checklist for `zitro-admin`, run against a live
> dev/staging server — not the automated Vitest/Playwright suite (that's `AD-TEST-001`/`002`,
> still `[ ]`). Written by reading the shipped code (`app.routes.ts`, the `@zitro/admin-ui`
> lib's components/templates, `AdminApiService`), not by transcribing `ADMIN-TASKS.md`'s
> original spec — every scenario and every `data-testid` below was verified against real
> source. Where the shipped screen falls short of its own task spec, that's called out inline
> as a **known gap**, not written as if the missing feature exists.
>
> **Status reference:** `ADMIN-STATUS.md` — AD-000 through AD-019 are `[x]` done (two of
> those, AD-013/AD-017, are intentional placeholders — see §6.2/§6.6); AD-020 (Firebase
> Hosting deploy) is `[ ]`, see §8. `zitro-superadmin`'s own test doc
> (`SUPERADMIN-TEST-SCENARIOS.md` §2) does a shallow smoke pass over these same screens since

  fixable from application code (no Cloud Console access). It affects `zitro-customer`'s
  existing `AddAddressPage` identically — same console warning there, confirmed side-by-side.

  independently of this — an admin who drops a pin without the town auto-filling can still

      in §9.1 to check the permission-boundary gap.

**Conventions used below**

- `[data-testid="..."]` — verified present in the component's template. Every testid quoted
  below was grepped out of `apps/libs/admin-ui/src/**/*.{ts,html}` directly — none are
  invented from the `ADMIN-TASKS.md` spec.
- **Most screens built after AD-010 ship with little or no `data-testid` coverage** on their
  own inputs/buttons — only the generic `data-table`/`data-table-row` testids apply. Where
  that's the case the scenario says so explicitly and gives you the visible label or `id`
  attribute to use instead — this is a real, confirmed gap (see §9.4), not a testing miss.
- Destructive actions (`deactivate`, `delete`, row-remove) go through the browser's native
  `confirm()` dialog, not a custom confirmation UI — despite AD-000 calling for a shared
  `confirmation-dialog` component. Dismissable in a real browser; if you're driving this with
  Playwright, native `confirm()` needs `page.on('dialog', ...)` handling, not a selector.
