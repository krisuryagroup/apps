# ZITRO Customer — Manual / Real-Time Test Scenarios

> **Purpose:** a human-executable QA checklist for `zitro-customer` (Android + Web), run against a
> live dev/staging server — not the automated Jest/Playwright suite (that's `TEST-001`/`TEST-002`
> in `UI-TASKS.md`, still `[ ]`). This app is the original, already-shipped, live-on-Play-Store
> customer app — **all 16 UI-\* page tasks are marked `[x]` done** in `UI-STATUS.md`, so every
> scenario below was written by reading the actually-routed source (`app.routes.ts`, the real
> `.page.ts`/`.component.ts` files, and real `data-testid` attributes), not transcribed from
> `UI-TASKS.md`'s specs or from `apps/ACCEPTANCE-TEST-SCENARIOS.md` (a pre-implementation spec
> document — several of its assumptions do not match what actually shipped; see §16).
>
> Several scenarios specifically probe **real-time behavior**, since that's the highest-value gap
> in an already-live food-delivery app: does the order-tracking screen update itself when the
> restaurant/delivery partner changes the order status, without the customer manually reloading?
> The short answer, confirmed by reading the code: **no, not currently** — see §9 and §16.1, the
> single most important finding in this document.

---

## 0. Before you start

**Environment**

- [ ] `zitro-api` running locally or against staging (`environment.ts` → `apiUrl:
    'http://localhost:8080'`; prod → `https://api.zitroapp.in`).
- [ ] `nx serve zitro-customer` running (Web). For Android, an APK/emulator build via Capacitor —
      most scenarios below are written web-first; flag anything Android-only.
- [ ] Firebase project `the-hunger-point` reachable — Phone Auth, Firestore, Realtime Database,
      and Storage are all provisioned in `app.config.ts` (`provideAuth`, `provideFirestore`,
      `provideDatabase`, `provideStorage`). Note: Realtime Database is provisioned but — per
      §9 — **nothing in this app actually reads or writes to it**. Don't spend time hunting for
      what uses it; nothing does yet.
- [ ] A second device/browser or `zitro-api`-side admin access to manually flip an order's status
      (via Postman against `PUT /api/admin/orders/{id}/status` or equivalent, or via
      `zitro-restaurant`/`zitro-admin` if available) — required for every real-time scenario in
      §9, since the app itself never triggers status transitions.

**Test accounts / data needed**

- [ ] One real Indian mobile number you can receive OTPs on (Firebase Phone Auth / Fast2SMS
      backend path — see §3 for which path is active).
- [ ] A "fresh" phone number that has never signed up before, to test the sign-up flow (UI-003) —
      if you reuse a number across test runs, you'll always land on `/home`, never `/auth/signup`.
- [ ] At least one order already placed and progressed to each status in the pipeline (`pending`,
      `confirmed`, `preparing`, `shipped`, `delivered`, `cancelled`) for the order-history/
      order-tracking/order-confirmation scenarios — otherwise you're only ever testing `pending`.
- [ ] A saved address in `houseAndStreet`/`town` shape (§11) and, ideally, a second saved address
      of the same `type` (e.g. two "Other" addresses) to probe §2's testid-collision note.
- [ ] A coupon code seeded server-side with a `minOrderAmount` you can straddle (order above and
      below it) and one that's expired/usage-capped, for §7's validation scenarios.

**Conventions used below**

- `[data-testid="..."]` — query the element by this attribute; where the app uses
  `[attr.data-testid]="'prefix-' + value"` (a dynamic id), the scenario says so explicitly.
- Business slugs from the platform seed: `hunger_point` (The Hunger Point, restaurant),
  `efc-pizza` (EFC Pizza, restaurant), `tularam-kirana-store` (Tularam Kirana Store, grocery).
- **Client-side cache to remember:** `OrderApiService.getOrder()` caches each order for 5 minutes
  (`ttlHours: 1/12`) in `localStorage`/memory (`CacheService`). If you flip an order's status
  server-side and reload the _same_ order-tracking tab within 5 minutes, you may see the stale
  cached order even though the real-time gap in §9 is the primary reason it won't update — don't
  conflate the two. Hard-reload or wait out the cache to isolate which one you're testing.
- Where a scenario references a route not reachable through any button in the UI, it says so —
  don't assume you missed a button; check §16 first.
